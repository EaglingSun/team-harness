# 지적 설명 루브릭 — 고친 판

PR 검수 Agent 가 남긴 지적의 설명(message)을 채점한다. 항목마다 따로 판정하고, 항목 하나에는 판단 하나만 둔다(1일차 이론 덱 163쪽). 판정 전에 이유를 먼저 쓴다. 설명의 길이는 판정에 쓰지 않는다.

판정: 합격 · 불합격 · 모름

## 항목 유형

설명한 문제가 그 지적의 `rule` 칸 규칙이 다루는 문제인가.

- 합격: 설명한 문제를 `rule` 칸 규칙(팀 코딩 규칙 원문)이 다룬다. 규칙 번호만 쓴 설명도 그 번호가 `rule` 칸과 같으면 합격이다
- 불합격: 설명한 문제를 다른 규칙이 다루거나, 어느 규칙도 다루지 않는다
- 모름: 설명이 무슨 문제를 말하는지 읽을 수 없다
- 경계 예: `rule` 이 숫자 리터럴 규칙인데 설명이 「함수 머리 주석이 짧다」면 불합격이다 — 주석은 숫자 리터럴 규칙이 다루지 않는다

## 항목 이유

설명이 `rule` 칸 규칙의 어느 조건을 코드의 무엇이 어기는지, 둘 다 말하는가.

- 합격: 어긴 대상(값 · 이름 · 주석)과 어긴 조건(규칙 원문의 조건)을 둘 다 말한다. 고칠 사람이 설명만 보고 무엇을 어떻게 고칠지 안다. 줄 번호는 지적의 `line` 칸에 있으므로 대상으로 치지 않는다
- 불합격: 둘 가운데 하나라도 빠졌다. 규칙 번호만 쓴 설명, 같은 말을 늘려 길기만 한 설명, 다른 규칙의 조건을 말한 설명은 불합격이다
- 모름: 바뀐 코드를 보고도 설명이 가리키는 대상을 찾을 수 없다
- 경계 예: 「s_count 라는 변수 이름이 있다」는 대상은 짚었지만 어긴 조건이 없어 불합격이다. 「함수 본문의 지역 배열 크기에 64 를 숫자로 직접 썼다」는 대상(64)과 조건(함수 본문 지역 배열 크기의 0 · 1 밖 숫자 리터럴)을 둘 다 말해 합격이다

## 쌍 비교

같은 자리의 설명 둘을 위 두 항목으로 각각 판정한다. 합격 항목이 많은 쪽을 고르고, 같으면 비김이다. 놓인 순서와 길이는 판정에 쓰지 않는다.
