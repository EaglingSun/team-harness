# PR 검수 Agent 통과 기준

- 통과선은 측정하기 전에 사람이 정한다. 측정 결과를 본 뒤에 통과선을 바꾸지 않는다(1일차 이론 덱 154쪽)
- 아래 값은 예다. 팀이 정한다(155쪽). 덱 155쪽 예와 다른 점 — 이 실습은 사례마다 한 번 측정하므로 「오탐/회」 대신 오탐 수 0 을 쓰고, `compare.py` 의 판정 불가가 덱의 「형식 오류」다
- `run_cases.py` · `judge.py` 가 이 표를 읽어 지표마다 통과 · 미달을 판정한다. 지표 칸의 `키` 와 통과선 칸의 `비교식` 은 지우지 않는다. 읽지 못하면 두 스크립트는 종료 코드 2 로 멈춘다

| 지표 | 계산 | 통과선 | 미달이면 |
|---|---|---|---|
| 판정 불가 `cannot` | `compare.py` 가 판정 불가로 본 사례 수(Agent 답이 JSON 이 아님 · 실행 오류 · 실제 모델이 설정과 다름) | `= 0` | 실행 고장이다(159쪽 ERROR). Agent 원출력(`<사례>.agent.txt`)을 열어 형식 · 도구 오류를 본다 → 형식 위반(JSON 앞뒤의 설명 문장 · 코드펜스)이면 그 설정을 한 번 더 측정한다 — PR 검수 Gate 에서도 G1 ERROR 다. 도구 오류면 원인을 고친 뒤 그 설정을 다시 측정한다 |
| 정답 폴더 열람 `opened` | 측정 기록(`<사례>.opened.txt`)에서 Agent 가 `pr-review-cases/` 를 열거나 검색한 사례 수 | `= 0` | 그 측정은 버린다 → Agent 에게 줄 것 · 읽을 범위를 다시 정한다 → 그 사례를 다시 측정한다 |
| 검출률(Recall) `recall` | 일치한 기대 지적 ÷ 기대 지적(case-01 ~ 05 의 다섯 건 · 판정 불가 사례의 기대 지적도 분모에 넣는다) | `>= 0.75` | 원인 넷(174쪽) 순서로 본다 — 명세(정답이 틀렸나) → 전달(연 파일에 규칙 파일이 있나 · 그 규칙이 파일에 있나) → 행동(읽었는데 안 따랐나 → 검수 Agent 정의 · 프로젝트 규칙에 한 문장) → 판정(채점이 틀렸나) → 한 곳만 고친 뒤 고친 사례와 전에 맞힌 사례를 다시 측정한다 → 끝으로 Held-out |
| 오탐 `false_pos` | 기대 지적에 없는 지적 수(지적이 없어야 하는 case-06 포함) | `= 0` | 위와 같은 순서 |
| Held-out `heldout` | Held-out 사례(case-07 — case-02 와 같은 CR-02 의 다른 형태: 함수가 아니라 파일 범위 변수이고, 이름이 `s_` 로 시작한다)에서 일치한 기대 지적 ÷ 기대 지적. 판정 불가 · 열람 · 오탐 줄도 함께 본다 | `= 1.0` | 정한 설정이 고칠 때 본 사례에만 맞는지 본다(172 · 174쪽). 한 번만 잰다. 틀리면 Held-out 은 소진됐다고 적고 설정을 되돌리거나 보완 갈래로 간다. 같은 case-07 로 다음 후보를 다시 재지 않는다 |
| 루브릭 합격률 `rubric_pass` | 루브릭 항목마다 합격 ÷ 채점한 지적(「모름」 · 오류 칸도 분모에 넣는다) | `>= 0.8` (예) | 판정을 먼저 의심한다 — Judge 지표가 통과했나 → 통과했으면 행동(검수 Agent 정의의 설명 지시)을 고친다 |
| Judge 일치율(Agreement) `agreement` | 사람 판정과 같은 판정 ÷ (연습 사례 × 항목). 「모름」 · 스키마 밖 답 · 호출 실패는 불일치로 분모에 남긴다 | `>= 0.8` (예) | 원인 「판정」이다. 갈린 사례를 읽고(166쪽 ③) 루브릭 문장을 고친다(163쪽) → 같은 연습 사례로 다시 판정한다(166쪽 ④). 통과하기 전에는 루브릭 채점(`judge.py actual`)을 믿지 않는다 |
| Judge 일관성(Consistency) `consistency` | 연습 쌍마다 두 설명의 순서를 바꿔 두 번 비교해 같은 쪽(또는 두 번 다 비김)을 고른 쌍 ÷ 연습 쌍. 오류가 난 쌍은 다르게 고른 것으로 센다 | `= 1.0` (예) | 원인 「판정」이다. 놓인 순서에 끌리는지(165쪽 위치 편향) · 루브릭 항목 하나가 판단 둘을 담았는지(163쪽) 본다 → 고친 뒤 다시 판정한다 |
| Judge 오류 `judge_errors` | 스키마 밖 답 · 호출 실패 · 시간 초과 칸 수 | `= 0` | 실행 고장이다 — 지표를 믿지 않는다. `judge.py` 를 `--resume` 으로 다시 실행해 남은 칸만 채운다 |

- Held-out 사례: `case-07`
- 「늘 합격만 주는 채점자」의 일치율을 함께 출력한다. 일치율 하나만 보지 않는다(166쪽 흔한 실수)
- 설정 고르기(173쪽): 통과선을 모두 넘는 설정 가운데 비용이 가장 낮은 것, 같으면 평균 초가 짧은 것. `run_cases.py --compare` 가 이 규칙으로 「적용 후보」를 표시하고, Ablation 도 이 후보 설정에서 한다. 고르는 사람은 나다 — 표를 보고 정하고 까닭을 평가 묶음에 쓴다
- 설정마다 한 번 잰 값이다. 적용 후보가 통과선 바로 위(놓침 · 오탐 한 건 차이)면 그 설정만 한 번 더 재서 같은지 본다(171 · 178쪽). 판정 불가 하나(형식 위반)로 미달한 설정도 한 번 더 잰다

## 테스트 순서

1. 이 표의 통과선을 먼저 확인한다
2. 측정한다 → 지표마다 통과 · 미달을 본다
3. 미달이면 그 줄의 「미달이면」 순서로 원인을 찾고, 한 곳만 고친다
4. 같은 사례 · 같은 채점으로 다시 측정하고 전후를 나란히 놓는다
5. 설정을 정해 검수 Agent 정의에 적용한다 → 그 커밋으로 Held-out(case-07)을 한 번 측정한다
6. 측정한 설정과 결과를 PR 로 올린다
