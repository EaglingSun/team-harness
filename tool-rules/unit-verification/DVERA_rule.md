# DVERA 사용 규칙 — 단위 검증

팀 도구 사용 규칙의 하나다. CT DVERA 를 쓸 때 도구가 맡는 일과 사람이 정하는 일, 팀이 겪은 문제로 정한 규칙(`DV-NN`)을 둔다. 점검 대상은 6절 `DV-NN` 이고, 1 ~ 5 절과 7절은 설명이다. DVERA 셋업을 마친 뒤에는 6절을 점검표로, Jenkins 게시 계획에는 검수 기준으로 쓴다. 규칙마다 지키는지, 어기는지, 빠졌는지 확인한다. 지적할 때는 규칙 번호를 붙인다. 셋업 일반 규칙은 `setup-rules.md`(`SU-NN`)다.

## 1. 도구 역할

- CT DVERA 는 테스트 도구 CT 의 AI 에이전트다. Claude Code 안에 Skill(재사용 지시 묶음) 18개와 `lct` 명령으로 들어온다
- 테스트는 CT 가 실행하고 커버리지(Coverage)를 측정한다. DVERA 는 Claude Code 안에서 그 작업을 준비하고 요청한다
- 사람이 하던 「요구사항 → 테스트 케이스 → 실행 → 추적 표」를 맡는다. 요구사항 문서에서 요구사항을 등록하고, 요구사항마다 단위 테스트를 만들어 CT 로 실행하고, 결과 · 커버리지를 남기고, 요구사항과 테스트의 연결을 기록한다
- 사람이 검토하는 것은 AI 가 만든 테스트의 의도 · 데이터 · 기대값이다. AI 가 만든 테스트는 CT 가 실제로 실행한 결과와 측정한 커버리지로 확인한다

## 2. 맡는 시험

- V 모델 단계: 단위 검증(구현과 짝). 정적 분석과 같은 단계다. CT 는 통합 시험도 맡지만 이 실습은 단위 시험만 쓴다
- 이 실습에서 쓰는 시험: 요구사항 기반 단위 테스트 · 커버리지가 빈 곳을 채우는 테스트 · 요구사항이나 코드가 바뀐 뒤 테스트 수정
- 커버리지: CT 는 구문 · 분기 · MC/DC(변경 조건/결정)를 측정한다. MC/DC 는 CT 화면에서, 파일별 구문 · 줄 · 분기 · 함수 수치는 `lct ci report` 결과 파일에서 본다
- 표준: 프로젝트 설정에서 적용 표준과 등급을 고르면 그 등급의 생성 지침 · 검증 지침이 프로젝트에 들어온다. 표준은 ISO 26262(차량 기능 안전 표준) · DO-178C(항공 소프트웨어 표준) · 표준 없음 가운데 고른다

## 3. 인터페이스

사람 · Claude Code · DVERA · Jenkins 가 무엇을 어떤 방법으로 주고받는지다.

| 주고받는 쪽 | 방법 | 예 |
|---|---|---|
| 사람 → Claude Code | 말로 요청하고, 에이전트가 멈추고 물으면 답한다 | 「이 저장소에 DVERA 초기설정을 해 줘」 |
| Claude Code → DVERA | Skill `dvera-*` 가 `lct` 명령을 실행한다. 사람은 이 명령을 직접 치지 않는다 | 초기설정 · 요구사항 등록 · 테스트 생성 · 실행 |
| 설치 확인 | Claude Code 가 실행해 출력을 보여 준다 | `lct config status` · `lct doctor` |
| Jenkins 빌드 | Jenkinsfile 의 단계가 실행한다 | `lct ci run` · `lct ci report` |
| 결과 | `lct ci report` 가 만든 파일 · CT 화면(`lct ct open`) | `ci-report.html` · `ci-report.agent.txt` · `junit.xml` · `cobertura.xml` |
| 기록 | 저장소의 `.lct/` | 설정 · 요구사항 · 테스트 · 요구사항과 테스트의 연결 기록 |

## 4. 워크플로

DVERA 를 들여 쓰는 작업 순서다.

1. 설치 · 전역 설정 — `DV-01` ~ `03`
2. 초기설정: 빌드캡처(빌드를 따라 하며 컴파일 인자를 기록) → 툴체인(컴파일러 · 링커 같은 빌드 도구 묶음) 정보 생성 → 모듈 정의 생성 → 분석 → 적용 확인 컴파일 — `DV-04` ~ `09`
3. 요구사항 등록 → 테스트 생성 → 실행 → 실패가 요구사항 쪽인지 코드 쪽인지 판정
4. 요구사항 보완 · 커버리지 보완 — 제품 코드는 고치지 않고 요구사항 · 테스트만 더한 뒤 PR(병합 요청)로 병합한다
5. 실패 수정 · 요구사항 변경 · 형상 변경 뒤 테스트 수정 — 코드 변경을 PR 로 올려 검수를 거쳐 병합한다(`DV-10`)
6. Jenkins 빌드에서 시험 결과 · 커버리지로 빌드를 판정한다 — `DV-11` · `12`

## 5. 사람이 정하는 것

- 적용 표준 · 등급(`DV-05`)
- 클린 빌드(산출물을 지우고 처음부터 하는 빌드) 명령 — 환경 준비와 make 명령(`DV-06`)
- 어떤 문장을 요구사항으로 볼지(요구사항 추출 기준)
- 실패가 코드 잘못인지 요구사항 잘못인지. 통과시키려고 기대값을 바꾸지 않는다
- 요구사항 문서를 고칠지
- 요구사항에 없는 동작의 규칙(예: 제동 중)
- 요구사항이 바뀐 뒤 진행 순서
- 커밋할 파일 · PR · 병합(`DV-09` · `DV-10`)
- Jenkins 빌드 판정 기준

## 6. 사용 규칙

### 설치 · 설정

- DV-01 설정은 설정 화면 대신 명령으로 한다 — CT 위치는 `lct config ct`, 테스트 생성에 코딩 에이전트의 LLM 을 쓰는 설정은 `lct config test-generator --llm agent`. 확인은 `lct config status` 의 `license full` · `ct set` · `test_generator agent` 세 줄과 `lct doctor` 의 `agent Claude Code installed` 줄이다
- DV-02 `lct license show` · `lct license register` 를 실행하지 않는다. 오류 창이 뜨고 사람이 닫을 때까지 멈춘다. 라이선스는 CT 화면에서 설정하고 `lct config status` 의 `license` 줄로 확인한다
- DV-03 DVERA 를 설치하면 설치 폴더가 사용자 PATH 에 등록된다. 설치한 뒤에는 새 PowerShell 창에서 `lct` 를 실행하고, 설치 전에 띄운 Jenkins 는 새 창에서 다시 띄운다. 설치 전에 연 창은 `lct` 를 찾지 못한다

### 초기설정

- DV-04 다른 폴더나 다른 PC 에서 만든 초기설정 자산으로 「환경 재적용」을 하지 않는다. 이 저장소에서 초기설정을 처음부터 한다
- DV-05 에이전트가 적용 표준 · 등급을 물으면 사람이 답한다. 코드 · 문서에서 짐작하게 두지 않는다
- DV-06 빌드캡처에 줄 클린 빌드로, 컴파일러 폴더를 PATH 앞에 다시 넣는 빌드 스크립트를 그대로 주지 않는다. 그 스크립트가 캡처용 래퍼보다 앞에 원본 컴파일러를 두어 빌드캡처가 `nothing_captured` 나 `capture_bypass_detected` 로 끝난다. 환경 준비(컴파일러 폴더를 PATH 에 넣는 명령)와 make 명령(clean · 빌드)을 따로 답한다. 에이전트가 같은 취지로 제안하면 그 제안을 고른다. 빌드 스크립트는 고치지 않는다. 분석 호스트 GCC 는 빌드에 쓰는 고객 컴파일러의 `gcc.exe` 를 그대로 등록한다. DVERA 설치본 GCC(4.7.2 · 5.3.0 · 9.5.0)는 고객 컴파일러 GCC 15.2 보다 낮아 호스트로 쓸 수 없다
- DV-07 한글이 든 UTF-8 소스에서 분석 첫 실행이 실패하면 분석 설정 파일을 손으로 고치지 않는다. 에이전트가 보정한 뒤 다시 실행하게 둔다
- DV-08 DVERA 작업은 한 번에 하나만 실행한다. `.lct/` 아래 자산 · 잠금 파일을 손으로 고치거나 지우지 않는다
- DV-09 `.lct/` 를 통째로 커밋하지 않는다. 다른 PC 와 공유할 초기설정 자산과 요구사항 · 테스트 연결 기록만 커밋하고, 무엇이 그것인지는 에이전트에게 묻는다. 이 예제에서 초기설정 뒤 `.lct/` 는 50MB 가 넘었고 대부분이 이 PC 의 작업 파일이었다

### 작업 범위

- DV-10 `SU-04` 가 막는 것은 빌드 환경을 맞추려고 README 의 「고치지 않는다」 폴더를 고치는 것이다. 요구사항이 바뀌었거나 DVERA 시험 결과에 따라 `test_ref/` · `src/` · `include/` · `tests/` 를 고치는 것은 작업 브랜치에 커밋하고 PR 로 올린다. 병합은 사람이 한다

### 결과 · Jenkins

- DV-11 Jenkins 빌드에서는 `lct ci run` 앞 단계에서 `.lct/workspace/path-vars.json` 에 그 PC 의 컴파일러 위치를 쓴다. 이 값은 PC 마다 다르다
- DV-12 Jenkins 는 `lct` 가 PATH 에 있고 CT 라이선스를 설정한 사용자의 창에서 띄운다

## 7. 실습에서 배운 것

강사가 실측에서 겪은 일과 그때 정한 규칙이다. 수강생이 실습에서 찾은 것은 프로젝트 규칙(`VSM-NN`)에 쌓고, 팀 규칙에 올릴 만한 것은 학습 후보의 반영 후보 칸 머리에 「팀 하네스 후보:」를 붙여 적는다.

| 겪은 일 | 정한 규칙 |
|---|---|
| 설치 프로그램의 설정 화면을 거치고도 CT 위치 · 라이선스가 설정되지 않은 채 남았다 | `DV-01` |
| `lct license show` 가 CT 오류 창을 띄우고, 사람이 창을 닫을 때까지 멈췄다 | `DV-02` |
| 설치가 설치 폴더를 사용자 PATH 에 등록했다 | `DV-03` |
| 초기설정 자산이 든 사본에서 초기설정을 맡기자 빌드캡처를 건너뛰고 환경 재적용으로 갔고, 이 PC 의 컴파일러 위치 값이 비어 멈췄다 | `DV-04` |
| 에이전트가 적용 표준의 근거를 저장소에서 찾다가 없자 사람에게 물었다 | `DV-05` |
| 예제 빌드 스크립트가 원본 컴파일러 폴더를 PATH 맨 앞에 다시 넣어 캡처용 래퍼를 덮는다고 에이전트가 짚었다 · 설치본 GCC 대신 예제의 컴파일러를 분석 호스트로 등록했다 | `DV-06` |
| 한글이 든 UTF-8 소스에서 분석 첫 실행이 실패했고, 에이전트가 보정한 뒤 성공했다 | `DV-07` |
| CT 로 결과 열기가 실패한 뒤 `.lct/` 에 잠금 파일이 남았다 | `DV-08` |
| 초기설정이 만든 `.lct/` 대부분이 이 PC 의 작업 파일이었고 `.lct/` 안에 `.gitignore` 가 없었다 | `DV-09` |
| 새로 받은 사본에서 `lct ci run` 이 이 PC 의 컴파일러 위치 값이 없어 멈췄다 | `DV-11` |
| Jenkins 게시는 `lct` 가 PATH 에 있고 CT 라이선스를 설정한 사용자의 창에서 띄운 Jenkins 로 확인했다 | `DV-12` |
